# 首场“桌面被黑洞吸入”与电影化场景导演方案

**状态：仅需求分析与实施方案，未实施。**

**日期：2026-09-28**

**配套文档：** `docs/research/gargantua-accretion-disc.md`（实施前应与本文一起评审）。

## 1. 已归一化的需求

### 目标体验

1. 屏保启动的**第一个场景**先展示启动前可见的当前屏幕内容。
2. 该内容在约 **5–10 秒**内被一个固定构图的黑洞自然吸入；若黑洞被导演为“更远”，整段过程可以更长。
3. 吸入过程必须能看见引力透镜：屏幕内容、恒星或尘埃在事件视界附近被拉伸、偏折和吞没，而不是简单全屏淡出。
4. 第一个场景结束后，桌面图像永久退出；后续仅使用自然的宇宙黑背景、稀疏恒星和低对比度尘埃。
5. 黑洞不再在屏幕上无目的漫游，也不随机改变镜头构图；每个场景的黑洞位置、大小、盘倾角和盘滚转角均为**有意设计且在场景内稳定**的值。
6. 后续场景可以改变布局构图，但应通过电影式转场切换，而不是让黑洞横越整个屏幕飞到新位置。
7. 整体基调应庄严、稀疏、低饱和、慢节奏；黑洞允许占据很大的画面，甚至局部出框，但不能长期缩小成装饰性小物体。

### 本方案采用的工作定义

- “当前屏幕内容”按**启动屏保前的一次静态桌面快照**理解，而不是连续录屏，也不是只吸入程序化背景。
- 第一个场景只在一次 `/s` 全屏屏保启动时播放一次；后续场景循环时不得重播桌面快照。
- “与黑洞距离有关”按**画面中的表观距离**定义：以固定黑洞焦点为中心，离焦点更远的屏幕区域更晚被吞没；整体时长由该开场镜头的“表观相机距离/黑洞起始尺寸”艺术参数决定。
- 现有程序只创建主显示器大小的全屏窗口。因此第一版只截取和呈现**同一目标显示器**；虚拟桌面/每显示器屏保是后续扩展，不应在本功能中隐式加入。

## 2. 为什么这能形成“吸入”而不是普通淡出

普通 `fade to black` 不满足需求：它没有物质向视界汇聚的方向性，也会使透镜在数学上存在、视觉上却无可偏折的内容。

开场应由以下三层共同构成：

1. **冻结的桌面源**：启动前的一帧桌面图像作为临时背景纹理。
2. **已有的相对论透镜路径**：桌面纹理应在现有光线追踪计算出的背景采样坐标处取样，而不是在最终画面上叠一层扭曲滤镜。这样桌面中的文字、窗口边缘和图像会在黑洞周围以与星空相同的方式弯曲。
3. **向内推进的吸收前沿**：由焦点向外扩展的、经过平滑化的消失时间表。被前沿扫过的内容只在事件视界/盘面附近保留短暂拉伸和压暗，随后被宇宙背景替代。

桌面快照是叙事性视觉素材，不应被标注为真实天体物理观测；透镜、盘面遮挡、Doppler 和非均匀吸积盘仍由现有/配套着色器模型承担。

## 3. 推荐开场时间模型

令 `F` 为本开场固定的黑洞中心，`uv` 为当前使用的左上原点归一化屏幕坐标，`aspect` 为屏幕宽高比：

```text
r = length((uv - F) * vec2(aspect, 1))
d = clamp(r / rVisibleMax, 0, 1)
T = mix(5 s, 12 s, openingDistance)
tArrive(d) = mix(tNear, T, pow(d, gamma))
```

建议初始值：

- `tNear`：约 0.6–1.0 秒，避免开场第一帧立即变黑；
- `T`：默认 8 秒；近景/大黑洞可为 5–7 秒，远景/小起始黑洞可为 10–12 秒；
- `gamma`：约 `0.7–1.1`，用于控制中心附近先被拉入、远处内容较晚消失的节奏；
- 前沿宽度：使用 `smoothstep` 的宽过渡，而非硬圆形擦除。

这定义的是**整段开场**的时长，而非让每个像素独立等待 5–10 秒。黑洞中心附近先发生强透镜和吞没，画面远端最后消失；因此观众会读成“画面落入深井”，而非由外向内的遮罩动画。

`openingDistance` 是艺术参数，不是假装已有精确相机距离的物理量。现有渲染器没有可直接使用的场景相机距离，因此在真正引入相机模型前，应明确将它作为镜头节奏控制量。

## 4. 首场分镜

| 阶段 | 建议时长 | 画面行为 | 目的 |
| --- | ---: | --- | --- |
| 静止建立 | 0.4–0.8 s | 显示冻结桌面；黑洞焦点已存在但极弱或在画外边缘显现 | 让观众确认“这是刚才的屏幕” |
| 透镜唤醒 | 1–2 s | 焦点附近先出现可辨认的弯曲、拉伸和暗化；不要立刻用高亮特效盖住内容 | 让引力透镜可读 |
| 吸收推进 | 至 `T` | 桌面纹理依现有透镜采样坐标偏折；吸收前沿从近向远推进，局部纹理被压暗并落入视界 | 完成“被吸入”的叙事 |
| 宇宙显露 | 1–2 s，可与上段重叠 | 桌面源完全退出；稀疏恒星、低对比度尘埃和黑色背景留在透镜后方 | 将场景自然交给宇宙镜头 |
| 首个正片镜头 | 30–90 s | 固定构图的黑洞、吸积盘和宇宙背景 | 建立庄严的常驻节奏 |

### 开场构图建议

- 焦点不要沿当前 Lissajous 轨迹移动；开场全程固定在一个三分法位置，例如略偏右、略高于中线，给被拉向焦点的桌面保留足够负空间。
- 黑洞的表观半径应在开场期间有一次克制的、缓慢的推近，但中心不移动。大尺寸和稳定性比频繁缩放更有压迫感。
- 吸积盘可保持接近边缘视角，让上/下透镜像更清楚；色彩应以暗金、白热中心和深红边缘为主，避免霓虹色。
- 桌面中的细节可能包含高对比文字；只在镜头前半段保留其可读性，随后由透镜和黑暗压低，避免视觉像“桌面特效演示”。

## 5. 后续电影化场景

后续场景的背景全部是宇宙背景，不再使用桌面纹理；每个场景仍可包含黑洞和吸积盘。除非另行提出，不包含纯背景、无黑洞的长插段。

### 场景规则

1. **场景内固定**：`center`、盘倾角、盘滚转、目标尺寸和背景主题在一个镜头内保持不变；允许盘内物质共转、星点极慢变化和不超过数个百分点的呼吸式尺度变化。
2. **场景间切换**：先在旧构图位置淡出黑洞/盘，短暂保留宇宙黑背景，再在新构图位置淡入。不要对 `center` 做跨屏线性插值，否则会重现“黑洞到处乱飞”。
3. **确定性播放**：使用具名的场景顺序、明确的持续时间和交叉淡入淡出；不再以 hash 随机选择外观，也不让独立的大小/位置函数破坏构图。
4. **尺寸下限**：除过场外，黑洞和盘应始终构成画面主语。可以局部出框或占据大半屏幕，但不应长期退化为小于视觉焦点的图标。

### 初始镜头目录（供实施代理确认/调参）

| 场景 | 构图意图 | 黑洞位置/尺寸 | 背景与运动 |
| --- | --- | --- | --- |
| `OPENING_INGESTION` | 桌面落入深井 | 右侧三分位，开场固定，缓慢推近 | 临时桌面源 → 黑色宇宙 |
| `SOVEREIGN_EDGE` | 庄严的侧视盘 | 右中或左中，盘横越画面但中心稳定 | 稀疏星场、极弱尘埃；盘物质缓慢共转 |
| `HORIZON_MONUMENT` | 巨大、可局部出框的视界 | 接近中央但留有上/下负空间 | 深黑背景，只给少量可被透镜辨认的星/尘结构 |
| `DISTANT_SENTINEL` | 较远但仍具压迫感的构图 | 三分位，尺寸不低于定义的视觉下限 | 更宽的盘和少量背景层次，不使用频繁镜头运动 |

这些是导演意图，不是要求在首个实现中一次性加入四套复杂资产。第一版可只实现开场和一套稳定正片构图，然后再扩展为小型场景表。

## 6. 推荐技术路径

### 6.1 桌面快照：选 GDI `BitBlt` + 内存 DIB

对“一次性抓取一帧，然后交给 OpenGL 3.3 着色器使用”的目标，首选是：

1. 仅当命令行解析确认真实 `/s` 全屏模式时执行；`/p` 预览、`/c` 设置和调试预览不抓桌面。
2. 在创建、显示或置顶全屏屏保窗口**之前**，从目标显示器的屏幕 DC 同步复制一帧到 top-down 32-bit DIB section。
3. 使用 `SRCCOPY | CAPTUREBLT`；后者使普通 layered windows 尽量进入快照。
4. OpenGL context 就绪后，将这帧 BGRA 数据一次上传为纹理；动画期间不再持续采集。
5. 上传完成即释放 DIB/屏幕 DC；开场结束后删除 GPU 纹理。

这是一次性、同步的路径，适合当前单文件 Win32 + OpenGL 3.3 架构；不应为了单帧开场引入 DXGI Desktop Duplication、D3D11/GL 资源互操作或 WinRT frame-pool 生命周期。

**官方参考：**

- [`BitBlt` 与 `CAPTUREBLT`](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-bitblt)
- [`GetDC(NULL)` 获取整个屏幕 DC](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getdc)
- [`CreateDIBSection`](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-createdibsection)
- [高 DPI 桌面应用与 DPI awareness](https://learn.microsoft.com/en-us/windows/win32/hidpi/high-dpi-desktop-application-development-on-windows)

### 6.2 必要边界和降级

- 截图必须早于 `CreateWindowExA` 创建可见全屏窗口；否则快照可能已包含黑屏/屏保自身。
- 应在创建窗口前启用合适的 DPI awareness，避免高 DPI 环境下截图坐标被虚拟化。
- 对受保护内容、DRM、安全桌面或主动排除捕获的窗口，结果可能是黑块、空白或系统决定的内容；这是正常降级，不能尝试绕过。参见 [`SetWindowDisplayAffinity`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity)。
- 若捕获、DIB 分配、纹理创建或上传失败，直接从宇宙背景开场，不重试、不报错打断屏保。
- 快照不得写入磁盘、日志、注册表或网络；不得在开场结束后保留 CPU/GPU 副本。它只用于当前进程的一次视觉转场。
- 第一版以当前主显示器窗口为准。若将来支持多显示器，需明确选择“虚拟桌面一张纹理”还是“每显示器单独窗口/纹理”；虚拟屏幕原点可能为负，且尺寸可能超过 `GL_MAX_TEXTURE_SIZE`。参见 [multiple-monitor metrics](https://learn.microsoft.com/en-us/windows/win32/gdi/multiple-monitor-system-metrics)。

### 6.3 着色器如何让快照接受同一套透镜

现有运行时 shader 位于 `blackhole_screensaver.c` 的 `shaderSource` 字符串中；不是根目录 `blackhole_screensaver.glsl` 文件。它已在远场/近场路径中生成背景采样坐标，并分别调用程序化宇宙背景。

后续实现应抽出一个概念上的 `BackgroundSource(lensedUv, rayDirection, phase)`：

```text
opening active  -> sample captured desktop at lensedUv
opening ending  -> blend captured desktop with cosmic background
later scenes    -> sample cosmic background + stars/dust only
```

关键约束：桌面纹理必须用**透镜之后的背景 UV**采样。不能只在最终 `fragColor` 上施加屏幕涡旋，因为那会使桌面、星空和盘面遵循不同的空间规律，且会削弱当前近场多次盘面相交的价值。

### 6.4 需要新增、但应局部化的宿主能力

未来实现仅需在现有 C 文件内增加以下能力；不引入外部依赖：

- 一次性 `DesktopSnapshot` 生命周期：捕获、上传、释放；
- OpenGL 纹理函数/常量和 `sampler2D` uniform 的加载与销毁；
- `CinematicTimeline` 的时间起点与阶段状态；
- 向嵌入式 shader 传递“有无快照、开场进度、当前场景”的少量 uniform。

现有 `renderFrame()` 已将单调时间传给 `iTime`。但其起点在窗口创建期间设定；为了让“5–10 秒”从第一张可渲染快照开始计时，应让开场拥有独立的时间 epoch，设在纹理上传和 shader 初始化成功之后。

## 7. 场景导演的最小深模块

为避免再次把位置、大小、盘外观和时间分别写成互不关联的函数，应建立一个概念上的 **`CinematicTimeline` 模块**。它的 interface 只提供给渲染器一个已经导演好的结果：

```text
SceneState at(elapsedSeconds) -> {
  phase,                 // OPENING / SCENE / SCENE_TRANSITION
  progress,              // 当前阶段的 0..1 进度
  layout,                // 固定 center、size、inclination、roll
  look,                  // DiskLook
  backgroundMode,        // DESKTOP_CAPTURE 或 COSMIC
  openingCaptureWeight
}
```

其 implementation 可以先是嵌入 shader 内的静态场景表，不必立刻扩大 C/GL uniform interface。桌面快照本身例外：它必然由宿主提供纹理和有效标志。

这个 seam 的目的不是抽象化，而是保证：

- 一次性开场不会被当前 `mod()` 演示循环重新播放；
- 一个镜头的布局由一个场景条目共同拥有，而不是被独立的随机 preset、大小波形和 Lissajous 漫游互相破坏；
- 后续加场景时不会接触光线追踪、盘面交点、透镜和色彩合成的核心实现。

## 8. 与当前代码的对应关系

当前可执行 shader 的场景选择、大小和位置逻辑集中在 `blackhole_screensaver.c` 的嵌入式 `shaderSource` 中：

- `demoLook()`：hash 驱动的盘外观选择；
- `demoSize()`：独立的周期性大小变化；
- `center` 的 Lissajous 计算：黑洞跨屏漫游；
- `p` / `pr` 之后：光线构造、弱场偏折、近场积分、盘面相交和颜色合成。

实施应以“用 `CinematicTimeline` 的结果替换前三项”为 seam，**保留** `p` / `pr` 以下的透镜和测地线逻辑。非均匀吸积盘则按配套研究文档在盘面交点的 `density` 位置接入；不要把盘的团块、桌面吸收或场景布局混成一个屏幕空间效果。

## 9. 分阶段实施计划（供后续主代理执行）

### 阶段 0：锁定视觉合同

- 确认第一版只支持当前主显示器，且“当前屏幕”是一次性静态快照。
- 确认 `/s` 播放一次开场；`/p` 跳过开场并显示代表性宇宙镜头；后续场景不重播桌面。
- 选择一张开场构图和一张常驻构图，确定 `T`、`openingDistance`、焦点位置和尺寸下限。
- 提供或确认 2–4 张参考画面，尤其是“庄严”与“透镜仍可见”的标准。

**验收门槛：** 时间、显示器范围、重播行为和场景含义不再含糊。

### 阶段 1：确定性时间线和静态构图

- 用非重复的开场阶段 + 具名后续场景替代周期性 hash/漫游模型。
- 在不引入桌面纹理前，先确认黑洞在一个镜头内不移动，场景切换时不跨屏飞行。
- 将首场和后续场景的背景模式显式化。

**验收门槛：** 反复运行时，镜头顺序、布局和持续时间完全可预测；开场不会在 later loop 中重现。

### 阶段 2：一次性桌面快照管线

- 在 `/s` 创建可见全屏窗口之前，用 GDI 抓取目标显示器；处理 DPI、top-down 像素布局和失败降级。
- 在 OpenGL 初始化后上传纹理；实现资源销毁和“不落盘”的生命周期。
- `/p`、`/c` 和失败路径不触发快照。

**验收门槛：** 正常桌面可在首帧出现；失败时平滑进入宇宙背景；不遗留截图文件或日志。

### 阶段 3：透镜化吸入转场

- 将桌面纹理接入已有 lensed background sampling，而不是后处理涡旋。
- 按第 3 节的距离时间表实现平滑的吸收前沿、可读透镜和桌面→宇宙背景交接。
- 先使用一套克制参数；不要在此阶段加入粒子爆炸、夸张扭曲或屏幕空间噪声。

**验收门槛：** 普通桌面、文本窗口和图片区域在黑洞附近可见拉伸/偏折；整段在目标时长内结束；其余画面不会像全局淡出。

### 阶段 4：后续庄严镜头

- 实现首个稳定常驻构图，再逐一加入小型场景表。
- 场景切换采用淡出到宇宙背景再淡入，不对黑洞中心做长距离插值。
- 结合 `gargantua-accretion-disc.md` 的团块密度方案，使盘面具有非均匀物质感，但不破坏场景稳定性。

**验收门槛：** 至少一次完整播放中没有桌面重现、黑洞乱飞、随机角度跳变或缩成装饰物的镜头。

### 阶段 5：验证

- 通过项目既有 `build.bat` 构建；检查 shader 编译日志。
- 手工验证 `/s`、`/p`、`/d`，以及至少 16:9、超宽屏和高 DPI 环境。
- 录制或截图检查 5–12 秒开场的节奏、透镜可读性、桌面退出、场景切换和长期运行稳定性。
- 不将编译产物、桌面截图或无关配置改动作为此功能的一部分。

## 10. 尚待产品确认的问题

下列问题不阻止先做本文档中的技术设计，但在代码实现前应由需求方确认：

1. 是否接受第一版只处理当前主显示器，而不是整个多显示器虚拟桌面？
2. 默认开场时长希望是约 8 秒，还是应固定为 5、10 或更长的具体值？
3. 黑洞首场焦点希望偏左、偏右还是接近中央？是否有《星际穿越》以外的明确构图参考？
4. 后续场景是自动按固定顺序切换，还是需要未来提供手动/配置选择？本文默认自动固定顺序。
5. 是否接受 `/p` 预览跳过桌面快照？本文建议跳过，以避免在 Windows 屏保设置中意外截取完整桌面并避免长开场看起来像黑屏。

## 11. 明确不在本次方案范围内

- 连续桌面录制、实时把用户操作吸入黑洞；
- 规避受保护内容、DRM 或 capture-exclusion；
- 完整 DNEG/DNGR/Kerr 光束追踪重写；
- 因本功能而增加外部依赖、遥测、截图持久化或大量配置滑块；
- 现在直接修改 `blackhole_screensaver.c`、编译 `.scr` 或替换发布产物。
